## Context

The app renders with `vita2d` in immediate-mode, blocking `while(SCE_TRUE)` loops — one per screen (`Menu_DisplayFiles`, `Menu_PlayAudio`, `Menu_DisplaySettings` and its five sub-menus). Each loop draws with hardcoded pixel coordinates and flat `vita2d_draw_rectangle` fills (no corner radius), reads input via `Utils_ReadControls`/`Touch_Update`, and screens call each other directly and block until the callee's loop returns (e.g. `Menu_DisplayFiles` calls `Menu_PlaySettings`... actually `Menu_DisplaySettings`, which itself calls each of its five sub-screens). `vita2d` has no native rounded-rectangle primitive; every stateful visual today (toggle/radio buttons, battery level, playback icons) is already a pre-rendered PNG texture rather than a drawn primitive. The only bundled font is `res/Roboto-Regular.ttf`. See `proposal.md` for why this is changing now.

## Goals / Non-Goals

**Goals:**
- Implement the four specs (`ui/nav-shell`, `ui/now-playing`, `ui/folder-browser`, `ui/settings`) faithfully to the provided mockups' visual language (palette, radii, chips/badges, typography).
- Introduce just enough shared drawing/data-driven scaffolding that three screens plus a rail don't each re-duplicate style constants and list-menu loops — directly addressing the duplication that made `menu_settings.c` the repo's lowest-health file.
- Leave `source/audio/*`, `source/fs.c`, `source/utils.c`, and `config.h`'s semantics untouched.

**Non-Goals:**
- Library, Playlists, or a mutable Queue — no scanning, indexing, or persistence engine of any kind.
- Any new audio-layer data (e.g. exposing bit depth/sample rate, or exact duration for formats that need a decode pass to know it) — format badges use only the file extension, which is already available.
- A general-purpose navigation stack / screen state machine. Three destinations don't need one yet.
- Dynamic, per-track accent color extraction from cover art — the accent is one fixed color (`#FF9166`), per the later static mockups.

## Decisions

**Rounded corners via 9-sliced textures, not draw-time primitive composition.** `vita2d` has no rounded-rect primitive, and the codebase's existing convention for every stateful visual is a texture, not a drawn shape. A small set of corner-radius tile textures (e.g. one ~10px-radius tile family for chips/rows, one ~18-28px-radius family for cards) gets drawn as 9 quads per element — four fixed-size corners, four stretched edges, one stretched/tiled center — via `vita2d_draw_texture_scale` against sub-regions of those tiles. This reuses the existing texture pipeline with no new rendering primitive and scales to the mockups' variously-sized cards/pills/buttons without needing one texture per exact size. Alternative considered: composing rounded rects at draw time from a rectangle plus four filled circles — more flexible for arbitrary radii, but corner anti-aliasing quality under `vita2d`'s default pipeline on real hardware is unverified, and it's a new drawing primitive this codebase has never used. Kept as a fallback if 9-slicing proves to need an impractical number of discrete tile sizes.

**One shared master-detail driver replaces the five duplicated settings loops.** A single data-driven screen (an array of `{category label, current-value hint, detail renderer, input handler}`) replaces `Menu_DisplayDeviceSettings`/`DisplaySortSettings`/`DisplayMetadataSettings`/`DisplayALCModeSettings`/`DisplayAudioSettings`. Reskinning each of the five loops in place was considered and rejected — it would restyle the exact duplication problem this change is also meant to retire, under a new coat of paint.

**Keep the existing "blocking loop calls the next screen's function" architecture.** The nav rail becomes shared chrome drawn and hit-tested inside each of the three top-level loops (Now Playing, Folders, Settings); selecting a different rail destination calls that destination's function directly, the same pattern `Menu_DisplayFiles` already uses to reach `Menu_DisplaySettings`. A proper navigation stack / state machine would be cleaner, especially once Library/Playlists add two more destinations, but is out of scope for a UI-only change with three mutually-calling screens. Flagged here as the natural point to revisit once the deferred functionality work adds more destinations.

**Filtering and format badges stay data-cheap.** The Folders filter matches substrings against the `File` linked list `Dirbrowse_PopulateFiles` already builds in memory — no re-read of the directory, no scan of subfolders. Format badges (Folders and Now Playing) are derived from the file extension already available via `FS_GetFileExt`/`file->ext`, not from parsed file headers — deliberately not reaching for the kind of "peek at file contents" work the deferred Library capability will need.

**Bundle two additional font files.** `Manrope` and `IBM Plex Mono` (both SIL Open Font License, safe to bundle statically) ship alongside `Roboto-Regular.ttf` and load the same way via `vita2d_load_font_file` at startup; each text draw call picks whichever loaded font object matches the mockup's usage (Manrope for labels/titles, IBM Plex Mono for numeric/technical strings like durations and format badges).

**The existing status strip (`StatusBar_Display`) is restyled, not respecified.** It keeps showing the same clock/battery/format-mode data it shows today; only its colors and type match the new palette. No new requirement was added for it since no observable behavior changes — it wasn't split into its own spec.

**Playback outlives the Now Playing screen; `Audio_HasTrack()` is the only new audio-layer surface.** The nav rail and Folders' docked mini-player both require that leaving Now Playing (cancel or rail) not stop playback. `vitaAudioLib` already decodes via its own registered callback, independent of which screen's loop is currently running, so this needs no new threading — just not tearing the session down on screen exit. `source/audio/audio.c`/`include/audio/audio.h` gained one `SceBool track_loaded` flag and `Audio_HasTrack()` (session-loaded, distinct from playing-vs-paused) so Folders/Settings/the rail can tell whether something is loaded; `Menu_PlayAudio` now tears down a previously loaded track only when opening a *different* one, and the final teardown runs once, in `main.c`, as a safety net right after the top-level `Menu_DisplayFiles()` call returns (covering the case where the user exits while a track is still loaded). This is the one place this change's "visual/navigation layer only" framing doesn't fully hold — see proposal.md's Impact section.

## Risks / Trade-offs

- [Risk] 9-sliced corner tiles may look visibly different from the mockups' CSS `border-radius` at small sizes on real hardware (pixel grid, no guaranteed anti-aliasing) → Mitigation: prototype the corner tiles on hardware before wiring up all three screens, and adjust baked radius/edge softness if needed.
- [Risk] Consolidating five settings loops into one driver could subtly change behavior at the edges (each loop today has slightly different item counts / paging math) → Mitigation: the settings spec's behavior-parity requirement is scoped per category; verify each of the five categories individually against its current behavior before deleting the old functions.
- [Risk] Three screens calling each other directly (instead of through a dispatcher) means adding the nav rail's "switch to any destination" behavior touches all three screens' loops symmetrically → Mitigation: acceptable at three destinations; becomes the forcing function for a real navigation stack once Library/Playlists are added later.
- [Risk] A folder with only one or two tracks will make Now Playing's "up next" preview look sparse or empty, which could read as a bug rather than an intentional state → Mitigation: design an explicit empty/short-queue visual state rather than leaving blank space.
- [Risk] Bundling two new font files grows the package size → Mitigation: both are OFL-licensed and small; acceptable for a homebrew distribution, but worth a quick size check once the actual files are chosen.
- [Risk] Removed the PS-button lock (`Utils_LockPower`/`Utils_UnlockPower`) that previously spanned the entire time a track was loaded. Confirmed on hardware: holding it for an indefinite background-playback session (rather than one bounded Now Playing visit) blocked the PS/Home button until the user navigated back to Folders and pressed START — this hard-locked the console once during testing. → Mitigation: removed the lock entirely from the playback path; PS-button behavior is now always normal, regardless of background playback. Residual risk: without it, a real PS-button suspend while decoding is active is now possible and untested — the old code prevented that scenario outright rather than handling suspend/resume, so its effect on `vitaAudioLib` across a real sleep/wake is unverified (worst case is audio glitches after resume, not a system hang).

## Open Questions
